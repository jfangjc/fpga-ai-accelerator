## Soak follow-up

The PS application follow-up measures the hardware counter/time ratio directly.
An independent **660-second** replay completed **66,079/66,079** frames with all
capture error/drop counters zero. Its 645 counter/time pairs span 651.462 s
after excluding startup/drain and fit to **15,999.747162 samples/s**, or
**-15.802 ppm** versus CLOCK_MONOTONIC (OLS standard error 0.605 ppm; frame
counter quantisation leaves 2.891 ms RMS residual). Raw pairs, capture counters
and the fit are in `clock-followup/monitor.jsonl`, `capture.txt`, `clock-fit.json`.
Reproduce with `python results/t2/followup_clock.py MONITOR --output JSON`.

The original 30-minute counter trace independently fits **-20.935 ppm**
(`soak/clock-fit.json`), with five-minute slopes from about -28 to -18 ppm.
Across the first/last bucket centres (1,500 s apart), this predicts **31.404 ms**
of artificial age increase; the observed p50 increase was **31.618 ms**.
The configured clock tree reports PL0 **99,999,999 Hz** and PL1
**149,999,999 Hz** (`followup/clocks.txt`); those nominal configuration values
are not a measurement against Linux time. Paced injection spaces accepted
samples by 6,250 PL0 cycles; the I2S path separately uses the fractional NCO
documented in the front-end specification. A 179.026 s read-only timekeeper
test measured CLOCK_MONOTONIC **+6.336 ppm** relative to CLOCK_MONOTONIC_RAW;
`timesync.txt` also records active NTP frequency discipline. This demonstrates
a timekeeper contribution; it does not separately calibrate both crystals.

The old anchor extrapolated the first-FFT sample-acceptance probe forever at
exactly 16 kHz. The new independent observer narrowly brackets hardware packet
counter transitions, averages them into one-second bins and fits a bounded
120-second window. It calibrates constant packet-compute delay against the
startup FIFO anchor and maps each update's oldest new sample to monotonic time.
It never fits application dequeue times, so consumer/inference queueing remains
in L_update. Startup uses the original anchor until ten bins exist and exports
`clock_fitted=false`; a missed FIFO probe still invalidates latency. The first
edge's <=2 ms bracket and FIFO probe limit absolute anchor accuracy. Capture
continuity/error counters and regression residuals must still be inspected;
the mapping is not evidence for uninterrupted input by itself.

The old stage array was already capped at 65,536 records, rather than an
unbounded leak. Its 72-byte records progressively touched about 1,038 KiB over
14,760 events, predicting **34.6 KiB/min**, close to the observed **33.0 KiB/min**
RSS slope. Stages now stream through the nice-10 writer and have no run-length
cutoff. A fixed, startup-resident 64 x 256 KiB log pool replaces per-event
strdup/free allocation. WAV storage remains proportional to replay duration;
phrase/inference buffers, writer storage and displayed transcript have explicit
bounds. This does not claim a general-purpose heap-leak audit.

The original logs identify **155 previews above 300 ms**, all following final
inference; **173 slow final updates** use per-layer fallback and **six** use
RUN_NETWORK. They only record cumulative merge deltas, so the 502 original
merge timestamps cannot be individually recovered. `soak/attribution.json`
preserves that limitation. New `merge_event` records identify the active final
and allocated phrase length for every replacement. Final feature generation,
backend requests and logits/CTC processing are unchanged. Preempting a long
final safely requires driver-level graph state/save-and-restore support; simply
changing FIFO priority cannot interrupt an already running request. No unsafe
chunking or changed final numerics were introduced.

## Final routing

The app now has a second CPU INT8 backend for long finals, separate from PL
preview inference. `--final-backend auto` keeps padded finals <=640 frames on
PL RUN_NETWORK and routes longer ones to the CPU worker. `cpu` routes every
final to CPU; `pl` retains the serial PL policy. The default CPU final pool is
three threads on cores 1-3, nice 5, leaving capture/output and inherited frontend
IRQ/injection affinity on core 0. The two-thread candidate used cores 2-3.
All backend calls have one owner; copied logits retire through a bounded
32-slot ordered ring. Feature input/output pools are pre-faulted, CPU maximum
activation extents are warmed, and glibc retains bounded frontend scratch.
The unsoaked output-buffer pre-faulting was kept; `malloc_trim(0)` was removed.

Exploratory 24-second runs on the same playlist, full framebuffer/TCP/log/stage/
PPM outputs, gave the following routing comparison. These are short runs,
not substitutes for the 30-minute acceptance workload. Evidence:
`final_routing/routing-comparison.json`.

## Out-of-order caption emission

Evidence: `results/t2/ooo_emit/`. This supersedes the ordered-emission
contract in the preceding final-routing section. The default remains
`--final-backend auto --final-threads 3`: the new full soak meets the 250 ms
preview stretch target while retaining zero merges. Long CPU finals remain
slower than the original serial PL finals; that trade-off has not disappeared.

The emitter can retire a ready preview or short PL final while an earlier CPU
final remains pending. The 32-slot copied-logit ring retains bounded storage
and reclaims only emitted leading slots. Each outstanding phrase owns its
stitch state and preceding-served sample anchor. The old final path performed
separate CTC decoding and did not supply tokens to the following phrase;
retaining per-phrase state preserves that independence and every stitch
operation. A late final cannot reset the next phrase's preview state.

Fig. 3 states now apply per phrase: Speaking has a stable preview and tentative
suffix; Finalising retains its last stable preview in amber as
tentative-committed; Committed replaces that phrase in place with white final
text. Later phrases continue beside pending ones. JSONL, TCP, SD log and PPM
share that caption model. Every event/snapshot carries `committed_prefix`,
`prefix_before_phrase` and phrase-indexed `segments` with state/text/tentative.
The terminal client marks pending phrases explicitly. `update_ms` still ends
at software framebuffer completion; physical scanout and TCP receipt are not
measured. The legacy `ordered_wait_ms` field now measures ready-to-emission
latency without a final barrier.
