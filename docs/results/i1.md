## Measurement limits

`irq_interval_us` uses capture-thread wake timestamps, including Linux scheduling
and coalescing; expect about 10 ms only at IRQ period 1. Existing `latency_avail`
and `latency_consumer` infer the last-sample time from first MM2S submission,
nominal/queried PL clock and 6250-cycle spacing. They are submission-referenced
estimates, not measured AXIS sample-accept timestamps. DMA startup and input
starvation bias them; no exact last-accepted-sample latency can be claimed from
this hardware interface alone. Record that qualification with any reported values.

No physical LED/button actuation or microphone clock/statistics check has run.
No RTL change was made.

## DMA tail-order correction and successful I1 (2026-11-02/03 AEDT)

Supersedes the earlier blocker/unmeasured statements above. Deployed hardware is
4a474b5, with optional SG status/control streams disabled, WNS +2.317 ns and
WHS +0.010 ns. No RTL or hardware source was changed in this follow-up.

Root cause: `put64` wrote MSB before LSB. In this 64-bit AXI DMA configuration,
TAILDESC_MSB is the fetch/restart trigger (PG021, MM2S_TAILDESC_MSB offset 14h).
The doorbell therefore used a stale low address. After clean PL load, TX BD0
completed (0x80004000), but unsubmitted zero-length BD1 was fetched and failed
(0x90000000); MM2S SR=0x15019, 14/24 frames. Repeated resets could also produce
an initial 536-byte RX packet with four spurious leading words. Writing low then
high fixes both symptoms. Descriptors already have correct 64-byte alignment,
64-bit next/buffer addresses, SOF/EOF, cleared status, and range cache maintenance.

Two consecutive bounded runs after the fix: 24/24 frames, FRAMES=24, STATUS=1,
MM2S CR/SR=0x15003/0x1100a, S2MM CR/SR=0x15013/0x10008; no DMA error bits.
`make -C sw/fedrv check-tail` checks both tail doorbells with a fake register file,
records actual write order, and uses an address with nonzero upper and lower words.
The board reproducer also rejects nonzero zero-input powers and DMA errors.

## 30-minute paced soak and power (2026-11-03, collected by the senior engineer)

Launched by the I1 worker inside the board mutex
(`flock /home/ubuntu/stt/board.lock sh /home/ubuntu/stt/fedrv/soak.sh 1800`), looping
the six I1 clips in 16 kHz paced mode; every captured frame is compared on the board
against `soak.ref.bin`, generated on the host by `model/frontend_fixed.py`
(`tests/i1/i1.py soakref`). The worker's quota ended mid-soak; the run
completed unattended and the logs were read from `~/stt/i1/`.

| Metric | Result |
|---|---|
| Duration / frames / IRQs | 1,800 s / 183,269 / 183,269 |
| Mismatched frames vs fixed-point reference | 0 |
| Sequence errors, ring overruns, consumer drops, TX underruns, mic overruns | 0, 0, 0, 0, 0 |
| `soak.exit` | 0 (`SOAK PASS`) |
| Capture-thread wake interval | mean 10,000.194 us, std 30.1, p50 10,000, p99 10,080, p99.9 10,100, max 12,381 us |
| Board power during soak (`power.sh`, 1 s samples, last 1,436 s) | mean 3.460 W, max 4.110 W |
| Idle power, stt-fe loaded (100 x 0.1 s) | mean 3.196 W, max 3.580 W |

Last-sample-to-user-space latency, FIFO-anchored probe (`tests/i1/latency_i1.c`,
100 trials, inside the mutex): the PL front-end sample counter is read with
CLOCK_MONOTONIC before/after the frame's last sample is accepted, bracketing the
acceptance time to <= 63.1 us. Result: mean 2.434-2.496 ms (lower/upper bracket),
max upper bound 3.615 ms. This is the front end's own contribution (FFT/mel compute,
S2MM DMA, IRQ, wake-up) to caption latency.

The soak's `latency_avail_us` (mean 21.9 ms, max 38.0 ms) and the clip run's
`latency_consumer_us` are referenced to the first MM2S submission of a long paced
injection, so they include injector queueing ahead of the PL; they are diagnostics,
not the front-end latency.

Not covered by I1 (by design): physical microphones (project tests by injection),
physical button presses.
